=== Cross-Origin Communication (CORS)

Frontend (Vite dev server, `http://localhost:5173`) and backend (FastAPI, its own port) run as separate processes with different origins. The backend explicitly enables CORS for the frontend dev origin, so the frontend can call backend routes directly via `fetch`/`axios` without needing a proxy.

=== Persistence and Schema Migrations

The SQLite schema is owned by versioned Alembic migrations in `backend/app/db/migrations/` (ADR-8); tables are never created implicitly.

* **Startup migrations.** On every start, `init_db()` brings the database to the latest revision before any request is served — the same path for `make backend`, tests, and the container. Migrations use the synchronous `sqlite3` driver in a worker thread, while the application itself stays on async SQLAlchemy (ADR-1).
* **Backup copy.** If the database file existed before the start and migrations are pending, it is copied to `<name>.bak-<revision>` next to it first (`<revision>` = the schema version the copy contains, `base` if none). Nothing is copied when no migration is pending or the database is new, and an existing copy is never overwritten. Copies are not cleaned up automatically.
* **Failure.** A failing backup or migration aborts startup with an error naming the path and the cause; the process exits non-zero. Recovery is restoring the matching copy and starting the previous release.
* **Integrity in the database.** Uniqueness, value ranges (`effort` 1–3, `kid_friendly` values), and link cascades are database constraints, so they also hold for direct SQL. SQLite enforces foreign keys only per connection: the application engine enables `PRAGMA foreign_keys=ON` on every connection, while the migration connection deliberately leaves it off, because batch-mode table recreation would otherwise cascade-delete link rows.
* **Constraint naming.** `Base.metadata` uses an explicit naming convention, so constraints have stable names that later batch migrations can address.
* **Case-insensitive text.** SQLite's `NOCASE` and `lower()` fold only ASCII. Where uniqueness must ignore case (tag names), the application stores an additional key normalized with Python's `str.casefold()` and the unique constraint sits on that key.
* **New revisions.** `cd backend && uv run alembic revision --autogenerate -m "..."`, review the generated file, commit it. A test compares the migrated schema with the models and fails when a model change has no revision.

=== Automated Testing

The project follows Test-Driven Development (red-green-refactor) on both sides of the stack:

* **Backend**: `pytest` + FastAPI's `TestClient`. The `TestClient` works unchanged against async-defined endpoints (it handles event-loop management internally), so no special effort is needed to test async routes. Starting point: a test for `GET /health` → `200 OK`.
* **Database**: model and migration tests run against temporary databases built by the real migrations, not by `create_all()`, so the constraints under test are the ones the migrations create.
* **Frontend**: Vitest, Vite-native and with first-class Vue 3 + TypeScript + Composition API support (see ADR-5).

=== Local Development Orchestration

A root `Makefile` bundles the start commands for backend and frontend (`make backend`, `make frontend`, `make dev` to start both processes in parallel). This replaces manually opening two terminals with the raw commands (`uv run uvicorn ...`, `npm run dev`) with a single documented entry point.

=== Frontend Architecture Style

Vue 3 components are written with the Composition API (`<script setup lang="ts">`) instead of the Options API. This groups logic by feature rather than by option type and gives better TypeScript type inference. State management via Pinia is deliberately deferred until a feature needs real cross-component state.
