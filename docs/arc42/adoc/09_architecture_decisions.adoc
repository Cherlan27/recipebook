=== ADR-1: Async SQLAlchemy instead of sync

*Context*: The backend needs database access to SQLite; FastAPI is an async framework.

*Decision*: SQLAlchemy 2.0 in async mode with the `aiosqlite` driver.

*Rationale*: Synchronous DB calls inside async request handlers block the event loop. The migration effort from sync to async SQLAlchemy is low on a new project (different connection URL, `await` on session calls); `TestClient` tests work unchanged.

*Consequence*: Migrations need a sync-driver workaround or an async-capable `env.py`. Resolved by ADR-8: migrations use the synchronous `sqlite3` driver in a worker thread.

=== ADR-2: Composition API instead of Options API

*Context*: The frontend is set up with Vue 3 + TypeScript.

*Decision*: Composition API with `<script setup>`.

*Rationale*: Better TypeScript type inference, logic can be grouped by feature rather than by option type, and logic is reusable via composables.

=== ADR-3: Pinia deferred

*Context*: There is no state-management need in the scaffold yet (only a `/health` check).

*Decision*: No Pinia setup in Issue #1.

*Rationale*: Avoids an unused abstraction; Pinia will be introduced once a feature (most likely the recipe list) needs real cross-component state.

=== ADR-4: Makefile for local development orchestration

*Context*: Backend and frontend should be startable both individually and together, locally.

*Decision*: Root `Makefile` with targets `backend`, `frontend`, `dev`.

*Rationale*: `make` is already available on the primary development machine (Windows, via Git Bash); alternative cross-platform tools (`justfile`, `concurrently`) were considered but dropped since `make` was already installed.

*Consequence*: Setup documentation should mention that `make` (e.g. via Git Bash/MinGW) is required.

=== ADR-5: Vitest for frontend tests

*Context*: The backend already has an automated testing approach (pytest + `TestClient`, ADR-1); the frontend test framework was still open.

*Decision*: Use Vitest as the frontend test framework.

*Rationale*: Vitest is Vite-native (shares Vite's config and transform pipeline), has first-class Vue 3 + TypeScript + Composition API support, and keeps frontend tests aligned with the project's TDD practice.

=== ADR-6: Layered backend structure

*Context*: Issue #1 only needs a `GET /health` endpoint, but is the first backend code in the project and shapes every follow-up issue.

*Decision*: Structure the backend into `app/api/routes`, `app/core`, `app/db`, and `app/models` from the start, rather than a single `app/main.py`.

*Rationale*: Follow-up issues (e.g. recipe CRUD) can slot into the existing layers instead of forcing a restructure of code that is not yet under test in its final shape.

=== ADR-7: Single-container deployment with the backend serving the frontend

*Context*: Issue #2 requires the application to run on hardware the owner controls (a Raspberry Pi in the home network), independent of an external cloud. Moving from local development to a deployed environment forces a decision that development never had to make: the frontend is a static build, and something has to serve it.

*Decision*: Deploy as a single container. A multi-stage build compiles the frontend and copies it into the Python runtime image, where the backend serves it as static files alongside the API on one published port. The image is built on the target device from source; application data lives in a bind-mounted host directory; the container runs as a non-root user.

*Rationale*: Same-origin delivery removes CORS as a production concern entirely — the alternative (two containers, CORS in production) would need the concrete home-network address in `cors_allowed_origins`, which is unknown at build time, changes with DHCP, and fails silently when wrong. A reverse-proxy split was considered and rejected as unneeded separation, since frontend and backend live in one repository and ship together.

*Consequence*: Frontend-only changes require rebuilding the whole image. CORS becomes development-only configuration. Full decision record at `docs/adr/0007-single-container-deployment.md`.

=== ADR-8: Alembic migrations applied at application start, with a backup copy

*Context*: Issue #3 introduces the first domain model. Since ADR-7 the deployed SQLite file persists in a bind-mounted directory, so schema changes must evolve a database that contains real data instead of recreating it. The Pi has no other backup, and SQLite migrations that recreate tables can fail half-way.

*Decision*: Manage the schema with Alembic. `init_db()` in the FastAPI `lifespan` applies pending migrations before any request is served — the same path for local development, tests, and the container, without an entrypoint script. Migrations use the synchronous `sqlite3` driver in a worker thread and live inside the `app` package (`app/db/migrations/`). Before pending migrations run against an existing file, it is copied to `app.db.bak-<revision>` next to the database (never overwriting an existing copy); a failing backup or migration aborts startup with an error naming the path and the cause.

*Rationale*: One start path cannot drift between environments, and a broken migration makes the instance visibly unavailable instead of running on an outdated schema. Keeping migrations in the `app` package means the existing image layout already ships them. The copy gives the Pi a restore point exactly when the schema is about to change.

*Consequence*: Backup copies accumulate (cleanup is out of scope); rollback means restoring a copy and starting the previous release. Full decision record at `docs/adr/0008-alembic-migrations-at-startup.md`.
