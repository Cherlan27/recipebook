=== Partially applied migrations on SQLite

*Risk*: SQLite DDL is not transactional under Alembic, and migrations that change existing tables recreate them (batch mode). A migration that fails half-way can leave the database partially migrated while it still records the old revision.

*Impact*: The instance does not start (ADR-8 aborts startup on a failed migration); the database file may be inconsistent.

*Mitigation*: Before pending migrations run, the existing file is copied to `app.db.bak-<revision>`, and an existing copy is never overwritten, so the last good state survives repeated failed starts. The copy is written under a temporary name, flushed, and then renamed, so an interrupted copy never counts as a backup, and a skipped backup is logged as a warning. Restore procedure: stop the instance, replace `app.db` with the copy named after the revision of the release you go back to (the oldest copy the failed deployment wrote), rename that copy (e.g. to `app.db.bak-<revision>.restored`) so the name is free for the next deployment, then start the previous release (README).

=== Foreign keys during batch migrations

*Risk*: Batch-mode migrations drop and recreate tables. With SQLite foreign-key enforcement enabled, dropping `recipes` or `tags` would cascade-delete every row in `recipe_tags`.

*Impact*: Silent loss of all recipe–tag links during an otherwise successful migration.

*Mitigation*: Foreign-key enforcement is enabled only on the application's connections; the migration connection switches it off explicitly (documented in `env.py`, covered by a test), and `PRAGMA foreign_key_check` after the upgrade fails startup if a migration left dangling links. Each new revision that alters existing tables gets a test that upgrades a database with data in place.

=== Accumulating backup copies

*Risk*: Every start with pending migrations leaves an `app.db.bak-<revision>` file in the data directory; nothing removes them.

*Impact*: Disk usage grows by one database copy per migrated release — small for a recipe database, but unbounded.

*Mitigation*: Accepted for now (cleanup was deliberately excluded from #3). The README documents the copies and that old ones can be deleted by hand, including the `app.db.bak-base` left by the first start on the Pi after this feature was introduced.

=== `make` dependency on Windows

*Risk*: Local development orchestration relies on `make`. On Windows, `make` is not available natively and must be installed separately (e.g. via Git Bash/MinGW).

*Impact*: New developers on a fresh Windows machine without Git Bash/MinGW may not be able to use `make dev` directly.

*Mitigation*: Document the requirement in the README; switch to a more cross-platform tool (`justfile`, `concurrently`) if this becomes a recurring problem.

=== SQLite on network-attached storage

*Risk*: The deployment's data directory is a bind mount from the host filesystem (see ADR-7). If it is pointed at an NFS or SMB share instead of local storage, SQLite's file locking is unreliable and can lead to database corruption.

*Impact*: Affects any deployment where the data directory is placed on network storage, e.g. a NAS share mounted into the host filesystem.

*Mitigation*: Documented explicitly in the deployment instructions (README) that the data directory must be on local storage.

=== No backup of deployment data

*Risk*: The bind-mounted data directory survives container restarts and image rebuilds, but this is not a backup. Volume removal (`docker compose down -v`), accidental deletion, or storage failure (e.g. SD card death on the Raspberry Pi) still causes data loss.

*Impact*: All recipe data on the deployed instance.

*Mitigation*: Stated explicitly in the deployment instructions so the persistence guarantee is not overread. Since ADR-8 a copy of the database is written before schema migrations, but it lives on the same storage and only exists for releases that migrate — it is a restore point for failed migrations, not a backup. Regular backups remain an unaddressed concern, to be picked up as their own effort if needed.

=== No authentication on the home-network deployment

*Risk*: The single-container deployment (ADR-7) has no authentication or TLS. Anyone with access to the home network can read and write all data.

*Impact*: Acceptable for the home-network scope this deployment targets; would not be acceptable if the instance became reachable beyond the home network.

*Mitigation*: Scope is deliberately limited to the home network. Public/VPS exposure with authentication and TLS is tracked as a separate issue (#5) rather than being retrofitted here.

=== Host/container UID mismatch on first deploy

*Risk*: The container runs as a non-root user with a configurable UID/GID, defaulting to `1000:1000` (the default account on Raspberry Pi OS, see ADR-7). If the target device's account uses a different UID/GID, the container cannot write to the bind-mounted data directory until the mismatch is resolved.

*Impact*: Affects first-time deployment on any device whose primary user account does not use UID/GID `1000:1000`.

*Mitigation*: The startup failure is diagnosable (it names the offending path, see the `deployment` capability spec). The deployment instructions document the one-time `chown` of the data directory and how to override the UID/GID in `docker-compose.yml`.
