== Deployment View

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The deployment view describes:

 1. technical infrastructure used to execute your system, with infrastructure elements like geographical locations, environments, computers, processors, channels and net topologies as well as other infrastructure elements and

2. mapping of (software) building blocks to that infrastructure elements.

Often systems are executed in different environments, e.g. development environment, test environment, production environment. In such cases you should document all relevant environments.

Especially document a deployment view if your software is executed as distributed system with more than one computer, processor, server or container or when you design and construct your own hardware processors and chips.

From a software perspective it is sufficient to capture only those elements of an infrastructure that are needed to show a deployment of your building blocks. Hardware architects can go beyond that and describe an infrastructure to any level of detail they need to capture.

.Motivation
Software does not run without hardware.
This underlying infrastructure can and will influence a system and/or some
cross-cutting concepts. Therefore, there is a need to know the infrastructure.

.Form

Maybe a highest level deployment diagram is already contained in section 3.2. as
technical context with your own infrastructure as ONE black box. In this section one can
zoom into this black box using additional deployment diagrams:

* UML offers deployment diagrams to express that view. Use it, probably with nested diagrams,
when your infrastructure is more complex.
* When your (hardware) stakeholders prefer other kinds of diagrams rather than a deployment diagram, let them use any kind that is able to show nodes and channels of the infrastructure.


.Further Information

See https://docs.arc42.org/section-7/[Deployment View] in the arc42 documentation.

****
endif::arc42help[]

=== Infrastructure Level 1

ifdef::arc42help[]
[role="arc42help"]
****
Describe (usually in a combination of diagrams, tables, and text):

* distribution of a system to multiple locations, environments, computers, processors, .., as well as physical connections between them
* important justifications or motivations for this deployment structure
* quality and/or performance features of this infrastructure
* mapping of software artifacts to elements of this infrastructure

For multiple environments or alternative deployments please copy and adapt this section of arc42 for all relevant environments.
****
endif::arc42help[]

[source]
----
Developer machine
├── make dev
│   ├── Backend process   (uv run uvicorn app.main:app --reload)  → :8000
│   └── Frontend process  (npm run dev / vite)                    → :5173
└── backend/data/app.db (local SQLite file)
----

Motivation::

Issue #1 has no production or server environment yet — only the local development environment. Backend and frontend run as two separate processes on the same machine.

Quality and/or Performance Features::

No deployment target in this issue; the focus is on a simple, reproducible local startup.

Mapping of Building Blocks to Infrastructure::

The backend process binds port `8000` (FastAPI/Uvicorn), the frontend process binds port `5173` (Vite). Both are orchestrated via the root `Makefile` (`make backend`, `make frontend`, `make dev` for a parallel start). The SQLite file lives locally under `backend/data/app.db`.

==== Home network deployment (Raspberry Pi)

[source]
----
Home network
└── Raspberry Pi (linux/arm64)
    └── Docker container (published port :8090)
        ├── Uvicorn (0.0.0.0:8000, internal)
        │   ├── GET  /*      → static files (built frontend, dist/)
        │   └── GET  /api/*  → FastAPI routers (e.g. /health)
        └── bind mount ./data → /app/data
                                  ├── app.db (SQLite, local storage only)
                                  └── app.db.bak-<revision> (copy before each migration, ADR-8)
----

Motivation::

Issue #2 (PBI-02): the application must run on hardware the owner controls, reachable from other devices in the home network, without depending on an external cloud. See ADR-7 for the single-container decision and the alternatives considered.

Quality and/or Performance Features::

* Frontend and API share one origin and one published port — no CORS configuration is needed in this environment (CORS remains a development-only concern, see Infrastructure Level 1).
* Application data (the SQLite file) is bind-mounted from the host, so it survives container restarts and image rebuilds. The bind mount must be on local storage — SQLite's file locking is unreliable on NFS/SMB shares.
* The container runs as a non-root user (UID/GID configurable, defaulting to `1000:1000`, the default account on Raspberry Pi OS).
* Pending schema migrations run on every container start, before the instance answers requests (ADR-8). Beforehand the existing `app.db` is copied to `app.db.bak-<revision>` in the same bind-mounted directory; a failing migration keeps the container from becoming healthy.
* Restart-safe is not the same as backed up: the data survives `docker restart`/`docker compose up -d --build`, but not volume removal or storage failure.
* Scope is the home network only; there is no TLS and no authentication (see PBI-05, #5, for the VPS/public-exposure case).

Mapping of Building Blocks to Infrastructure::

The image is built directly on the target device from source (`git pull` + `docker compose up -d --build`); no image is pushed to a registry. A multi-stage `Dockerfile` builds the frontend (`frontend/dist/`) in a Node stage and copies it into the Python runtime image, where FastAPI (`app/main.py`) serves it as static files alongside the API, mounted after the routers so `/health` and other API routes keep precedence. `docker-compose.yml` declares the published port, the bind mount, the `RECIPEBOOK_DATABASE_PATH` environment variable pointing into the mounted volume, and a `HEALTHCHECK`/Compose healthcheck against `GET /health`.
