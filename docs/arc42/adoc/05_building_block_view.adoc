== Building Block View

ifdef::arc42help[]
[role="arc42help"]
****
.Content
The building block view shows the static decomposition of the system into building blocks (modules, components, subsystems, classes, interfaces, packages, libraries, frameworks, layers, partitions, tiers, functions, macros, operations, data structures, ...) as well as their dependencies (relationships, associations, ...)

This view is mandatory for every architecture documentation.
In analogy to a house this is the _floor plan_.

.Motivation
Maintain an overview of your source code by making its structure understandable through
abstraction.

This allows you to communicate with your stakeholder on an abstract level without disclosing implementation details.

.Form
The building block view is a hierarchical collection of black boxes and white boxes
(see figure below) and their descriptions.

image::05_building_blocks-EN.png["Hierarchy of building blocks"]

*Level 1* is the white box description of the overall system together with black
box descriptions of all contained building blocks.

*Level 2* zooms into some building blocks of level 1.
Thus it contains the white box description of selected building blocks of level 1, together with black box descriptions of their internal building blocks.

*Level 3* zooms into selected building blocks of level 2, and so on.


.Further Information

See https://docs.arc42.org/section-5/[Building Block View] in the arc42 documentation.

****
endif::arc42help[]

=== Whitebox Overall System

[source]
----
┌─────────────┐   HTTP/JSON (/api)   ┌─────────────┐   SQLAlchemy (async)   ┌─────────────┐
│  Frontend   │ ───────────────────▶ │   Backend   │ ─────────────────────▶ │   SQLite    │
│  (Vue 3)    │ ◀─────────────────── │  (FastAPI)  │ ◀───────────────────── │   app.db    │
└─────────────┘                      └─────────────┘                       └─────────────┘
----

Motivation::

Separation of presentation (frontend) and application logic/data storage (backend) as two independent processes within the shared monorepo (`backend/`, `frontend/`) — independently runnable, but versioned together.

Contained Building Blocks::
[cols="1,3", options="header"]
|===
| **Name** | **Responsibility**
| Frontend | Vue 3 SPA (TypeScript, Composition API), provides the user interface and calls backend endpoints over HTTP/JSON
| Backend | FastAPI application, exposes REST endpoints, encapsulates business logic and database access via SQLAlchemy (async)
|===

Important Interfaces::

HTTP/JSON with relative URLs. Recipe endpoints live under `/api` (`GET /api/recipes`, `GET /api/recipes/{id}`); `GET /health` keeps its path. In development the Vite dev server proxies `/api` to `http://localhost:8000`, so `/api` needs no CORS; the CORS rule for `http://localhost:5173` stays for `/health` (ADR-7). In the container, frontend and API share one origin.

==== Backend

_Purpose/Responsibility_: Exposes the REST API, manages access to the SQLite database, sets CORS rules for the frontend.

_Interface(s)_: HTTP/JSON, e.g. `GET /health`, `GET /api/recipes`, `GET /api/recipes/{id}`.

_Directory/File Location_: `backend/`

_(Optional) Open Issues/Problems/Risks_: Schema migrations run at startup and can prevent it (ADR-8) — see <<section-technical-risks>>.

==== Frontend

_Purpose/Responsibility_: Provides the user interface, consumes the backend API.

_Interface(s)_: HTTP/JSON calls to the backend through relative `/api` URLs.

_Directory/File Location_: `frontend/`

Building blocks in `frontend/src` (ADR-9, no shared state, ADR-3):

[cols="1,3", options="header"]
|===
| **Name** | **Responsibility**
| `router.ts` | Vue Router in hash mode: `/` (overview) and `/recipes/:id` (detail)
| `views/RecipeListView.vue` | Overview of all recipes, with the empty-database and backend-unreachable hints
| `views/RecipeDetailView.vue` | One recipe with all filled fields, with the not-found and backend-unreachable hints
| `api/recipes.ts` | Typed `fetchRecipes()` and `fetchRecipe(id)`; throws `NotFoundError` on `404` and `BackendUnavailableError` on network errors and `5xx`
| `toLines` | Pure function that splits ingredients and steps text into non-empty lines
|===

=== Level 2

==== White Box _Backend_

The backend is internally layered to separate routing, configuration, database access, and domain models:

[cols="1,3", options="header"]
|===
| **Name** | **Responsibility**
| `app/api/routes` | HTTP endpoints (`health.py` for `GET /health`, `recipes.py` for the read-only `GET /api/recipes` and `GET /api/recipes/{id}`)
| `app/schemas` | Pydantic response schemas (`RecipeListItem`, `RecipeDetail`); tags are returned as sorted names, so the API shape does not follow model changes by accident
| `app/core` | Central configuration (e.g. CORS origin, DB path) via settings
| `app/db` | SQLAlchemy engine/session management (async, `aiosqlite` driver, SQLite foreign-key enforcement on every connection), declarative base with a constraint naming convention, `init_db()` called from the FastAPI `lifespan`
| `app/db/migrate.py` | Brings the database to the latest schema version at startup: detects pending migrations, writes the backup copy `app.db.bak-<revision>`, runs Alembic, and turns failures into a startup error (ADR-8)
| `app/db/migrations` | Alembic environment (`env.py`, synchronous `sqlite3` driver) and the versioned revisions in `versions/`; `backend/alembic.ini` points the developer CLI here
| `app/models` | SQLAlchemy models of the domain: `Recipe`, `Tag`, and the `recipe_tags` link table (see <<section-data-model>>)
|===

This layering is deliberately introduced already in the scaffold (Issue #1) so follow-up issues (e.g. recipe CRUD) can slot in without retrofitting the structure.

[[section-data-model]]
==== Data Model

Introduced in Issue #3 (PBI-03). The fields follow the existing paper recipe system so both stay compatible; only `nr` and `name` are required, so incomplete paper recipes can be captured. The schema is created and evolved exclusively by Alembic migrations (ADR-8).

[source]
----
recipes                         recipe_tags                      tags
──────────────────────────      ─────────────────────────        ──────────────────────────
id            PK          ◀──── recipe_id  PK, FK (CASCADE)
nr            int, unique,      tag_id     PK, FK (CASCADE) ───▶ id        PK
              required                                           name      trimmed, first
name          text, required                                               spelling kept
effort        int, CHECK 1-3                                     name_key  casefolded name,
time_minutes  int                                                          unique
servings      int
kid_friendly  yes | with_adjustments | no
ingredients   text, one line per ingredient
steps         text, one line per step
created_at    timestamp (UTC)
updated_at    timestamp (UTC)
----

[cols="1,3", options="header"]
|===
| **Table** | **Rules**
| `recipes` | `nr` is unique and required, `name` is required; `effort` is limited to 1–3 and `kid_friendly` to `yes` / `with_adjustments` / `no` by CHECK constraints; `ingredients` and `steps` are free text with one line per entry; `created_at` / `updated_at` are set by the application (UTC) with a database default as fallback.
| `tags` | Free-form, no fixed list. The name is trimmed and stored in the spelling of its first creation; `name_key` (the casefolded name) carries the unique constraint, so uniqueness ignores case including umlauts. Names are normalized to Unicode NFC first; `casefold()` makes `ß` and `ss` equal.
| `recipe_tags` | n:m link with a composite primary key (a tag is attached to a recipe at most once). Deleting a recipe or a tag removes only the links, enforced by `ON DELETE CASCADE`.
|===

Deliberately not part of the model yet: an image reference (added by #4), structured ingredients with quantities.
